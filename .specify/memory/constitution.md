# Kanjy Constitution

## Core Principles

### I. Done Is What the Student Sees

Every spec states an acceptance bar written from the student's screens: phone at 375 px first,
then desktop. A feature is done only when it was exercised end to end in a real browser at both
sizes, judged against that bar by reviewers who did not build it, with screenshots attached to the
Linear ticket. Passing builds or lint are the floor, not evidence. No new unit tests are written.

### II. Root Cause, Not Patches

No special cases, silent fallbacks or post-filters that hide a symptom (for example, falling back
to mock data when a lesson id does not exist). Every plan names the root cause it removes and how
the same class of failure becomes impossible or loudly visible.

### III. Plan Before Code

Spec and plan are approved by Noe before any implementation. Opus writes spec, plan and reviews;
Sonnet subagents implement approved tasks; Opus reviews every diff before it is merged.

### IV. One Source of Truth for Kanji Data

All kanji content (levels, meanings, readings, stroke data, vocabulary, lesson grouping) is
generated by one reproducible build script from pinned versions of open sources. The app never
contains a hand-edited copy of generated data. Human corrections live in a single overrides file
that the script applies, so a regeneration never loses them.

### V. Licenses Respected

Data derived from CC BY-SA sources (KANJIDIC2, JMdict, KanjiVG) keeps its license and attribution,
separate from the MIT-licensed code, and the app has a visible credits page. WaniKani content is
never shipped. JLPT levels are labeled as unofficial lists (there is no official list since 2010)
and their author is credited.

### VI. Keys Never in Text

Secrets live in the macOS Keychain on the Mac and in the host's variables in the cloud. Never in a
`.env`, a commit, a chat, a log, a screenshot or a command argument. Client-side public keys that
the platform designs to be public are still configured through host variables, never hardcoded.

### VII. Human Approval for Money and Exposure

Spending money, creating an account or cloud service, exposing anything to the internet, and
writing production data each require Noe's explicit yes, named in the plan.

### VIII. Design for Scale

Every list, library or collection is designed for 1,000+ items: search, filters, a dense view and
scrolling that holds up. The N1 level (1,232 kanji, 120+ lessons) is the design case, not a level
with five items.

### IX. Anti-Slop Design (NON-NEGOTIABLE)

- No middle dot used as a separator between words, anywhere (UI, docs, commits, code strings).
- No numbering for its own sake; a number appears only when it is the information needed.
- No cartoon names for features or people; plain names of what things do.
- No colored or gray accent bar on the left edge of cards, quotes or list items.
- No information repeated on one screen.
- Keyboard shortcuts appear only in hover tooltips, never as visible text.
- Less text: no counters, dates or metadata that do not help the next action; empty states show,
  they do not explain.
- No bordered box inside a bordered box; no hairline dividers as default structure.
- One clearly most important thing per screen; things that act look like buttons.

### X. No Vendor Names in the Interface

The UI never names the services it is built with. Say what happens in plain words. The only
exception is the credits page, where attribution is legally required by the data licenses.

### XI. Simplest Thing That Beats the Alternative

Prefer proven existing tools (a published spaced-repetition algorithm, a hosted auth and database)
over custom builds. A custom component is built only when it clearly beats the existing option.

### XII. Small, Traceable, Shipped Changes

Every commit carries a Linear ticket ID, is staged by file name (never `git add -A`) and is pushed
right after. Each validated feature is merged to main; no long-lived branches. Work happens in a
worktree created from `origin/main`.

### XIII. Spanish for Students, English for Code

The interface speaks plain, natural Spanish with no invented terms. Code, specs, plans and code
comments are written in English.

## Product and Data Constraints

- Stack: React 19, Vite, Tailwind CSS 4, TypeScript, React Router. Mobile-first web app, installable.
- Audience: the open public of Spanish speakers; no teacher or classroom role.
- Content: JLPT N5 to N1 (2,211 kanji in the Waller lists), lessons of about ten kanji ordered by
  usage frequency inside each level.
- Generated kanji data is split per level and loaded on demand; source dumps are never committed.

## Development Workflow

Spec Kit end to end: constitution, specify, clarify, plan, tasks, analyze, implement. Every
feature or fix starts from a Linear ticket. Verification follows Principle I. Design mockups are
made in Paper and approved by Noe before the matching UI is implemented. Before and after
screenshots of each redesigned screen go to the ticket.

## Governance

This constitution overrides other practices in this repository. Amendments are proposed in the
same turn that Noe states a new standing rule, approved by him, and versioned with semantic
versioning: MAJOR for removing or redefining a principle, MINOR for adding one or materially
expanding guidance, PATCH for wording. `/speckit-analyze` checks every plan against these
principles; a violation blocks implementation until it is resolved or Noe accepts it explicitly.
